## 优先发现

### F1 [P1] BroadcastSkipPolicy 全段跳过会绕过广播安全检查

位置：app/src/main/java/com/kooritea/fcmfix/xposed/BroadcastFix.java:339-371；识别逻辑位于 xposed/XposedModule.java:303-323。

在 beforeHookedMethod 中，只要 Intent 被判定为 FCM 且目标为空或在 allowList 中，就直接返回 false/null。原始 shouldSkipMessage 不会执行。AOSP Android 16 在该方法中检查接收器是否导出、发送方权限、AppOps、Intent Firewall、接收方 requiredPermissions 等；这些检查都会被跳过。

同时 FCM 判定只依赖 action 或 google.message_id / gcm.message_id / from + collapse_key 等可由普通应用构造的字段，没有校验发送方 UID/包名。普通广播可以伪装成 FCM 获得额外放行；目标未知时还会绕过用户选择的应用名单。

修复方向：保留原始安全检查；仅修复 stopped/background 相关路径。根据 BroadcastRecord 的真实发送 UID 和用户验证来源，按实际接收器解析目标，无法确定目标时不放行。不能用消息字段代替身份验证。

证据：
- [项目代码](https://github.com/yuangr/fcmfix/blob/744c9c28d8169292925c6c4469c29ea3bb16064f/app/src/main/java/com/kooritea/fcmfix/xposed/BroadcastFix.java#L357-L370)
- [AOSP Android 16 BroadcastSkipPolicy](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/services/core/java/com/android/server/am/BroadcastSkipPolicy.java#L113-L153)

### F2 [P1] 每次注册建立新拦截器，又在每个拦截器中遍历全部回调

位置：app/src/main/java/com/kooritea/fcmfix/libxposed/XposedBridge.java:48-81；重复注册入口：xposed/ReconnectManagerFix.java:89-90、149-171。

hookMethod 每次把 callback 放入共享 HOOKS 列表，同时安装新的 libxposed 拦截器。每个拦截器运行共享列表中的全部 callback。因此同一方法注册 n 个回调时，before/after 阶段各执行 n² 次。GcmChimeraService 重建后 checkVersion 会再次调用 startHook，没有幂等保护；心跳修正和 watchdog 任务会重复执行。

独立实验（实际桥接源码 + 简化运行时）：

```text
registrations=1 before=1 after=1 original=1 result=7
registrations=2 before=4 after=4 original=1 result=7
registrations=3 before=9 after=9 original=1 result=7
```

修复方向：每个 Executable 只安装一个底层拦截器，在里面分发稳定的回调快照，或者每个底层拦截器只处理自己的 callback；Hook 注册失败要回滚状态，解除注册要正确维护最后一个底层 handle。ReconnectManagerFix 另外需要幂等注册。

### F3 [P1] 冰箱解冻任务去重会丢弃后续推送

位置：app/src/main/java/com/kooritea/fcmfix/xposed/BroadcastFix.java:240-271。

触发条件：开启 includeIceBoxDisableApp，目标应用仍冻结，第一条消息的解冻任务未结束时又收到消息。

每条消息先 setResult(false) 阻止当前广播继续执行，但只有 compareAndSet(false,true) 成功的那条消息建立任务并重放自己的 param。其他消息没有进入等待队列，也不调用原始广播。结果是同一包名在解冻期间到达的不同推送被去重掉。

另外，当前优先选中的 broadcastIntentWithFeature 返回 int，提前返回 Boolean false 不符合返回类型。框架如何降级需要实机验证，但返回值类型本身确定不匹配。

修复方向：只合并“解冻操作”，按 userId + package 排队保留每条广播，解冻后逐条投递，超时明确处理；使用正确返回类型。重放需要保留原始身份并遵守原方法的线程与锁约束。

### F4 [P2] appOp 参数猜测可能修改 userId

位置：app/src/main/java/com/kooritea/fcmfix/xposed/BroadcastFix.java:175-180、231-234。

参数名不可用时，代码把最后一个 int 当作 appOp。Android 16 AOSP 的 broadcastIntentWithFeature 中 appOp 在索引 11，最后的 int 在索引 15，是 userId。在 userId == -1（USER_ALL）的调用上，会把 userId 改成 11，而 appOp 仍是 -1，导致错误的用户路由或发送失败。

使用无参数名元数据的 Java 签名实验：

```text
namesPresent=false guessedAppOpIndex=15 realAppOpIndex=11 realUserIdIndex=15
appOpAfter=-1 userIdAfter=11
```

这是有明确触发条件的问题，不代表当前手机普通 userId=0 的每条推送都受影响。

修复方向：移除无必要的 appOp 改写；如确实需要，使用验证过的完整签名映射，匹配失败就禁用该改写，避免猜最后一个 int。

[AOSP 签名](https://github.com/aosp-mirror/platform_frameworks_base/blob/android16-release/services/core/java/com/android/server/am/BroadcastController.java#L662-L667)

### F5 [P2] watchdog 延迟任务没有取消或合并

位置：app/src/main/java/com/kooritea/fcmfix/xposed/ReconnectManagerFix.java:195-217。

每次 GMS 重设心跳/连接超时都 schedule 新任务，返回的 ScheduledFuture 被丢弃，没有取消旧任务。单线程调度器限制了线程数，但其延迟队列仍可积累，任务还持有定时器对象。结合 F2 重复注册，会放大额外任务数量与重连检查。

修复方向：按定时器实例/报警类型保存唯一 Future，新超时取消旧任务；使用代次检查阻止旧任务触发重连，启用取消任务的队列移除策略。未测量实际电量影响，不能据此给出耗电百分比。

### F6 [P2] 配置加载中的后续更新会被忽略

位置：app/src/main/java/com/kooritea/fcmfix/xposed/XposedModule.java:176-209、229-245。

onUpdateConfig 在 loadConfigThread 非空时直接跳过本次请求。若线程已读取旧 allowList，而用户此时再次勾选并广播更新，第二次请求被丢弃；线程最后设置 init=true，没有补读机制。运行中的 Hook 可继续使用旧名单，直到下一次配置更新或重新初始化。

修复方向：增加 dirty/version 机制，处理期间发生变更就再次读取；将所有配置构建成不可变快照后一次交换。getBooleanConfig/targetIsAllow 中的 join(2000) 也应避免出现在系统广播的敏感执行路径。

### F7 [P2] 主分支提交不会触发现有 CI

位置：.github/workflows/android.yml:3-5。

当前分支与仓库默认分支为 main，工作流只监听 master 的 push，且没有 pull_request 或 workflow_dispatch 入口。因此向 main 提交修复不会自动执行此构建流程。

修复方向：监听 main 和 pull_request，增加手动触发；在发布前执行测试与构建。

### F8 [P2] 常规测试源码目录被 Git 忽略

位置：.gitignore:19-20。

**/test/ 和 **/androidTest/ 会忽略 app/src/test 和 app/src/androidTest 中的源代码。通过普通 git add 新增回归测试不会把它们纳入版本控制，远端构建无法获得这些测试。

修复方向：移除这两个规则，仅忽略 build 生成目录。目前仓库没有已跟踪的单元测试或 instrumentation 测试。

## 其他需要改进的地方

- “包含 FCM”检测存在误报：MainActivity.java:215-240 把 AppMeasurementReceiver、任意 Firebase 命名组件及 com.tencent.mm 全部标为包含 FCM。这只能算组件线索，无法证明某个发行渠道实际注册了 FCM。建议界面写明“检测到相关组件”，避免“全选”制造不必要的唤醒许可。
- 多用户解冻不完整：IceboxUtils.java:61 在 system_server 内用 Process.myUid()/100000 得到的是主用户，不是广播目标用户；OplusProxyFix.java:422 还硬编码 userId=0。工作资料/分身用户需要从真实广播目标提取 userId/uid。
- MainActivity.java:363-393 在远端配置保存失败后仍保留内存中的修改，列表在 300 行继续翻转勾选状态。应在提交成功后更新 UI，失败时回滚。
- MainActivity.java:72 的服务监听器捕获 Activity，没有对应注销，重复打开界面可能留下旧实例回调；需要核对实际 service 库的生命周期约定并补清理。
- GmsForcePushFix 会修改 GMS 内所有匹配的包信息查询，没有独立开关，也不限定推送调用链；应缩小范围并提供可独立关闭的开关。
- OplusProxyFix 对 GMS 限制观察和更新做全局绕过，尚无耗电 A/B 实测。不能把“收到消息”直接等同于“更省电”。
- README 和仓库内旧审查报告没有对应到当前 v1.8 的精确状态。旧报告中的构造函数 before Hook、无权限配置广播等问题已修复，本报告没有重复计入这些旧问题。

## 对当前 ColorOS 使用的判断

项目的 stopped 广播修复和按消息解冻方向有实用价值。优先修复 F1/F2，再完善 F3/F4/F5；保留原始权限检查，避免为未知目标放行。当前消息已正常的应用不需要额外缩短心跳，也不能用永久 Doze 白名单代替正常的临时推送豁免。

与 ColorDozeManager 配合时，应分别验证：目标没有永久 Doze 豁免、真实 FCM 消息到达后仍能获得必要的临时执行机会、息屏文字与通话通知及时、目标完成处理后回到正常后台管理。两个模块的功能边界在源码上可以并存，未在本轮进行组合实机测试。
